# 评测划分规范（阶段 1.1：只定规范，不生成最终保留集）

本文件定义**评测数据如何划分、参考答案如何产生、保留集如何保持“未见”**。

当前状态：规范已定义，**尚未生成完整保留集，也尚未运行任何模型评测**。
本轮没有任何 LLM 调用。评测的执行机制留到阶段六。

---

## 1. 为什么要分三层

一个指标数字算对了，不代表 Agent 答对了业务问题；一个 Agent 在调试用的问题上答对了，
更不代表它在没见过的问题上能答对。所以数据分三层，各自只承担一件事。

| 层 | 名称 | 用途 | 谁可以看 | 状态 |
|---|---|---|---|---|
| A | 手工 fixture | 规则与计算的正确性验证 | 开发者、单元测试 | ✅ 已有（`eda/data/fixtures/*.csv`） |
| B | 开发集（dev set） | 提示词、流程、澄清逻辑的调试 | 开发者、Agent 调试 | ⬜ 待建（阶段三） |
| C | 保留测试集（held-out set） | 冻结版本后的最终评测 | **仅评测脚本**，不得进入任何提示词 | ⬜ 待建（阶段六） |

### A 层：手工 fixture

- 位置：`eda/data/fixtures/*.csv`，4 客户 / 5 商品 / 8 订单 / 12 明细；
- 参考答案：`tests/data/expected_fixture_metrics.json`，由**纸笔人工推导**得到，
  推导过程写在 `docs/metrics.md` 第 6 节；
- 用途：验证口径实现、过滤规则、去重规则、重复累计规则；
- **不用于**评价 Agent 的自然语言理解能力。

### B 层：开发集

- 用途：调提示词、调 LangGraph 流程、调口径澄清与错误修复；
- 允许反复查看、反复修改代码直到通过；
- 可以出现在提示词的 few-shot 示例里（如果确有必要）；
- 规模：几十个问题即可，覆盖常见问法与明显的歧义问法。

### C 层：保留测试集

- 用途：**在代码冻结之后**，一次性评测，用于报告最终指标；
- 保留集的问题、参考答案、错误分析结果，**都不得**进入：
  - 系统提示词或任何提示词模板，
  - few-shot 示例，
  - 检索示例库 / 相似问题库，
  - Agent 的任何输入（包括“参考口径”注入），
  - 代码中的条件分支或特例处理；
- 评测脚本读取保留集的路径与运行时代码完全隔离。

## 2. 保留集一旦被用来改代码，就失效了

这是必须写下来的纪律，因为它很容易被违反：

> **只要用保留集上的失败案例去定位并修改了代码、提示词或配置，
> 该保留集就不再是“未见测试集”，它已经降级为开发集。**

发生这种情况时的正确做法：

1. 在 `docs/progress.md` 中记录：哪一批保留集在哪次修改中被消耗；
2. 把这批问题正式并入开发集；
3. 构建**新的**保留集，然后才能报告新的“未见集”指标。

不允许的做法：
- 用保留集调完代码后，仍然把该保留集的分数报告为“未见集表现”；
- 把保留集里答错的题从保留集里删掉，然后重新报分数；
- 反复在同一个保留集上迭代，只报告最后一次的分数。

---

## 3. 新保留集怎么造（不是改写开发集问题）

把开发集的问题换几个词，只能测出复述能力。新保留集必须在这些方向上引入**真实的新变化**：

1. **新的问题组合**：把维度、时间范围、指标重新组合（例如「某类别在某地区的客单价环比」），
   而不是替换同义词；
2. **边界场景**：
   - 空结果区间（触发零分母策略），
   - 单日 / 跨年 / 闭区间端点，
   - 只含被排除状态（cancelled / refunded）的区间，
   - 不可加维度上的订单数提问（类别订单数），
   - 口径本身有歧义、应当触发澄清而不是硬答的问题，
   - 超出语义层能力范围、应当明确拒答的问题（例如预测、因果归因）；
3. **不同数据种子**：用 `--seed` 生成另一份演示数据，使「记住了某个具体数字」这种作弊失效；
4. **不同数据规模与分布**：例如把某个月份的订单量调到极低。

---

## 4. 参考答案怎么来

参考答案只有两个合法来源：

1. **人工核验的 fixture**：在小数据上纸笔推导（A 层的做法）；
2. **独立参考计算**：用与被测路径**不同**的方式重新算一遍，例如：
   - 直接对基表写 SQL，绕开分析视图（`tests/test_semantic_consistency.py` 里的
     `_reference_totals` 就是这种做法），
   - 或用 pandas 对 CSV 独立聚合。

**绝对不允许**：
- 让被测 Agent 自己生成“标准答案”，再拿它当基准（自我评分）；
- 用另一个 LLM 生成参考答案而不做人工核验；
- 把 Agent 第一次的输出固化成期望值（把 bug 固化成规范）。

参考答案必须带上**口径声明**：同一个问题在不同口径下有不同的正确答案，
因此期望值要写明用的是哪个指标 ID、哪个时间区间、端点是否包含、哪些状态被排除。

## 5. 评分维度（阶段六实现）

计划分开评，不混成一个分数：

| 维度 | 问题 | 为什么单独评 |
|---|---|---|
| 计划正确性 | 解析出的指标 / 时间范围 / 维度是否正确 | 口径错了，后面全错 |
| 执行成功率 | SQL 是否通过安全校验并成功执行 | 与答案正确性**不是**一回事 |
| 数值正确性 | 数字是否等于参考答案 | 这才是业务正确性 |
| 证据一致性 | 结论文字是否与实际查询结果一致 | 防止“数字对、话说错” |
| 澄清恰当性 | 该澄清时是否澄清，不该澄清时是否直接回答 | 两种失败都要罚 |
| 拒答恰当性 | 超出能力范围时是否明确拒答 | 防止编造 |

**自由 Text-to-SQL 只作为对照基线**，用于回答「加了语义层和确定性 SQL 编译到底有没有用」，
它不是默认执行路径。
